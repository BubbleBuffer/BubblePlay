# Follow active window

The browser's Monitors popover offers a default-off toggle when the host advertises `followWindow: 1`. The browser saves that choice and sends it on connection. Android currently has no toggle. Only the interactive user-level host advertises the capability; the older privileged-capture path does not.

## Host policy

The host samples the foreground window every 250 ms and chooses the monitor containing most of it. It ignores invisible, minimized, cloaked and shell windows, DWM's stand-in for a hung app (class `Ghost`, owned by `dwm.exe`, which otherwise sent the view to the ghost's monitor while the app was frozen), windows of the Snipping Tool executables (`SnippingTool.exe`, `ScreenClippingHost.exe`, matched case-insensitively; its editor window too), and any window covering at least 90% of two or more monitors (a screen-wide overlay such as the Snipping Tool capture layer), which keeps the current monitor and the last handled pair. A changed window/monitor pair must appear in two consecutive samples; automatic switches happen at most once per second. A manual monitor selection therefore persists until a subsequent focus or placement change.

Ordinary following waits until the move/resize loop and left-button hold have ended. It uses the same switch path as a manual selection: `desktop-state` with `monitor-switch`, then `monitor-switched` and `monitor-list`. The first confirmed pair after enabling follow also counts.

The implementation also contains an edge-hold carry path: during a window move, holding the cursor within 8 px of an edge with an adjacent monitor for 150 ms (jitter inside the zone does not restart the hold) switches the view and moves the cursor as if it had crossed between the two real monitors: on the crossed axis it lands 16 px (twice the edge zone) inside the target's facing edge, so leaving the right edge arrives at the left side of the target and leaving the top arrives at the bottom; on the other axis it keeps its desktop coordinate, clamped into the target. The dragged window comes with it. If the host cursor is already past the edge on another monitor (relative input can take it there), the view switches at once, without moving the cursor. Neighbours are found from the real monitor rectangles, not an assumed side-by-side layout. The log (info) records each move loop's start and end with the closest edge distance and whether a neighbour was found, and why an attempt did not switch (no neighbour, left the zone, resizing, already switched, cooldown). Clients that send absolute moves (the browser's Work mode) would otherwise snap the cursor back to their own pointer on the next move. From the edge switch until the move loop ends or the left button is released, the host therefore adds a pixel offset to absolute moves (the translated cursor position minus the position the client's last absolute position maps to on the new monitor), clamped to the desktop; consecutive switches in one drag replace the offset, and afterwards the next move lands at the client's true pointer. Relative moves (Game mode, and clients that never sent an absolute position) need no offset, and the secure desktop never uses one. No protocol change. It samples moves every 50 ms, shares the one-switch-per-second limit, preserves held input, excludes resizing and requires leaving the edge zone before rearming. This path has unit coverage; the retained development record does not establish live edge-hold acceptance.

## Carrying a drag past the screen edge (browser, trial)

A page cannot move the real pointer, so after an edge switch the user's pointer stops at their screen edge while the host cursor has been carried into the new monitor. In Work mode, when a `monitor-switch` arrives (in-place handshake) while a real mouse's left button is held, the viewer requests pointer lock on the input surface (`worker/public/drag-lock.js`, wired in `receiver.js`). The request is plain, without `unadjustedMovement`, so speed matches the pointer. While the lock is held the viewer hides the real cursor, draws its own, and sends relative motion through the usual motion path; button changes go without a position (a positioned button packet would get the host's drag offset added a second time). Later switches in the same drag keep the lock. The host needs no change: relative moves are injected from the cursor's current position and never take the absolute drag offset; the offset is cleared on the left-button release or `release-all`.

The lock ends on mouse-up (the normal release is sent first), and on Esc, focus loss, a hidden tab, a mode change, disconnect or any other loss of the lock, in which case the viewer sends release-all so the host never keeps a button down. A refusal (`pointerlockerror`, rejected request) does nothing more for that drag and is not retried. It does not touch Game mode's lock, label or keyboard capture. Each attempt writes one info line, `drag-lock`, with `granted`, `sinceDownMs` (time from the mouse-down to the request) and, on refusal, `error`. This measures how often Chrome's activation window refuses the request. After the lock ends, the real pointer reappears at the screen edge where it was locked, so the next absolute move after a drag lands there, as it already did without the lock. Unit tests: `worker/test/drag-lock.test.mjs`; live behavior is not yet verified.

## Monitor transitions in the browser

Both transports switch monitors in place on the existing WebRTC peer or WSS epoch. The browser keeps the last frame and runs a forced first-frame handshake for the new media generation. On WebRTC the host's `admitted` message (a `ctl` kind) carries the new IDR's RTP timestamp; native video opens the input gate only for a presented frame at or after it, and WebCodecs only after a keyframe at or after it. A frame presented after admission but from the old monitor therefore no longer opens the gate. If the host omits the timestamp, the browser cannot read `rtpTimestamp` from `requestVideoFrameCallback`, or the handshake fails, the browser restarts the peer in a new signaling epoch with input gated. Desktop-source transitions use the same gate ([secure-desktop.md](secure-desktop.md#in-place-desktop-transitions-on-webrtc)) but release held input.

Held keys and buttons survive the transition on the client. While the handshake gates input, `InputController` drops refused packets without recording gated presses. On presentation it sends release-all only if a held key or button was let go during the gate; otherwise it resumes without one, so a carried drag continues. The host's `CarriedInput` applies the same rule to packets that reach its own gate. After a non-carry switch the host has already released everything, so the client may still believe something is held. Its later release packets for that input are no-ops on the host. The Android client applies the same rule to `monitor-switch` and `monitor-switched` (`RemoteInput.resumeAfterTransition` and `Session.inputGated`, with JVM tests in `RemoteInputTest`); desktop-source changes and dead transports still release.

## Wire contract

- `host-capabilities.followWindow` (a `ctl` kind) is an integer version, absent when unsupported.
- Client sends, inside `ctl`, `{"type":"media-control","action":"follow","follow":true,"protocol":4,"epoch":"…","reason":"user-follow"}`; `follow` must be boolean and the epoch current.
- `monitor-list.follow` reports host state when supported.
- Host state starts off for each signaling session; clients that never send follow controls retain ordinary monitor selection.

[`host/src/follow_window.rs`](../../host/src/follow_window.rs) contains the decision logic and Win32 sampler. It maps the chosen monitor by device name, falling back to monitor origin. The [shared fixture](../../fixtures/follow-window-contract.json) and browser/host tests cover the capability and messages. Focus-driven following was reported working on a two-monitor host; that observation is separate from edge-hold or an independent packaged installation.
