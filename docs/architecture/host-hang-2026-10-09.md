# Host hang on 2026-10-09

Investigation at source HEAD `f25975b49a94dd5e67a774c457080dc29a86bf87`.
The installed host and tray were not changed or restarted.

## Evidence

The provided full-memory dump `host-39408.dmp` has 34 threads. Captured AMD64
PE unwind records were used to unwind the stacks through Windows thread entry;
the following findings are not just matches found by scanning stack bytes.

- Main thread **34988** waits in `NtWaitForSingleObject` through
  `WaitForSingleObjectEx`, `nvwgf2umx`, `d3d11` and `nvEncodeAPI64`.
  The host return address is RVA **0x1026ae**. The instruction at
  **0x1026a8** calls the encoder API table at offset **0x18**, the
  `reconfigure_encoder` entry. Parameter construction matches
  `Nvenc::set_bitrate`, including a requested bitrate of **795,177 bps**.
  Captured instruction bytes match the installed executable.
- Thread **44828** waits through NVIDIA/D3D11 and DXGI. Host RVA
  **0x135df4** calls COM vtable offset **0x40** with timeout **100 ms**:
  `IDXGIOutputDuplication::AcquireNextFrame`.
- Both threads wait on handle **0x438**, identified by the dump's handle
  metadata as an unnamed **semaphore**. It is not a Rust mutex. The dump
  does not identify its signaller or establish the driver's internal cycle.
- The independent secure-helper summary thread still logging is consistent
  with a blocked session owner: signalling, input and production are serviced
  by that owner, so an NVENC call that does not return starves all three.

The blocked path is proven. Concurrent DDA/NVENC access as the trigger is an
inference. NVIDIA's [threading guidance](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html#threading-model)
warns that cross-thread DXGI acquisition and NVENC bitstream operations on the
application's DirectX device can produce undefined behaviour; it does not
specifically identify reconfiguration or this driver deadlock.

The second dump, `host-46952.dmp` from the 2026-10-10 08:45:37 UTC freeze,
shows producer thread **8792** inside `NvEncRegisterResource` and capture
thread **59156** inside `AcquireNextFrame` with a **100 ms** timeout, both
waiting on unnamed semaphore **0x71c**. The NVENC call-table slot is **26**
(`ENCODE_API + 0xd0`), so this captured call is registration rather than
reconfiguration. Rapid 24 Mbps / 6 Mbps refine-rate toggles precede the freeze;
their role as a trigger remains unproven.

Committed HEAD `67a7202` retains the path: `run_serve` arms `request_event_frame_at` before its
activity wait, then consumes WSS bitrate events through `apply_wss_adjustment`
in `host_encode.rs`, which calls `Nvenc::set_bitrate`. Acquisition and bitrate
reconfiguration can therefore overlap. No Rust lock-order cycle was established
in the inspected capture, WSS, input and secure-helper paths.

The working tree uses one retained device gate for duplication, shared-device
copies and every NVENC operation, limits acquisition waits to 16 ms under it,
and keeps longer waits and parked housekeeping outside acquisition.
Shared immediate contexts have verified multithread protection through the
`ID3D10Multithread`/`ID3D11Multithread` interface. Queued bitrate, QP, profile
and reset settings coalesce into one reconfiguration immediately before a
frame's registration and encode; refine restoration waits for the next frame
and is superseded by another boost or a newer rate decision.

## Bounded failure handling and diagnostics

The admin-agent client had an independent definite defect: `CreateFileW`
opened a synchronous pipe; `write_client` called `write_all` before the nominal
reply deadline began. A peer that stops consuming requests can block that
write indefinitely. `File::flush` was also on this path, but the regression
did not establish that Rust implements it as a pipe flush. Polling with
`PeekNamedPipe` on the synchronous handle also did not guarantee a deadline.
These calls occur inline from the session owner's `InputSink::send_inputs`.

The client now encodes into memory and uses overlapped reads and writes with
one deadline covering each hello or injection transaction, including all input
chunks. Cancellation retains live buffers and handles until completion in a
fixed lock-free quarantine; exhaustion fails closed. Uncertain injection
delivery reports agent loss and never repeats the input locally. Agent trust,
session, policy and version checks are retained. No wire or client change is
required. Retaining cancelled storage follows the Windows
[CancelIoEx lifetime requirements](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex).
Failed attempts start the reconnect backoff at completion, so a slow hello
cannot consume that interval and make every queued input retry immediately.

The secure-helper client uses the same overlapped transport: hello has a
two-second write/reply deadline, background reads and writes are bounded at
500 ms, and polling leaves a partial frame queued rather than blocking for
its tail. SYSTEM owner, image, session and protocol checks are retained.

WSS media teardown waits at most 400 ms for its worker before detaching it
with its resources. A process-wide sixteen-worker limit also counts abandoned
connectors. A connect completed after stop cannot publish a media session.

Discarded DDA frames are destroyed after releasing the capture state mutex.
Native COM cleanup can therefore stall its worker without also preventing
the producer from accessing that state. This does not cancel the native call.

The session watchdog observes atomic progress from another thread. After ten
seconds without progress it records the session stage and source line, plus
the active NVENC call and its source line when applicable. It reports once per
stall, continues across ordinary parked housekeeping, and does not try to
cancel native encoder work or free resources still used by a driver.

Serialization prevents application-side overlap on the covered device paths.
It does not cancel an independently stuck native call; recovery from that
condition still requires a separate GPU ownership or isolation decision.

The capture review also found unbounded DDA-worker shutdown joins and
invalidation-thread startup/shutdown waits. Monitor changes, secure-desktop
suspension, and capture recovery can reach those waits. A timed join followed
by detachment is insufficient: recovery currently removes the waiter before
stopping it and can reopen duplication while an abandoned worker still owns
the old duplication/device. Safe recovery needs retained retirement state
that suppresses reopening until the old worker finishes, or process isolation.
That ownership decision remains outside this patch under the task's stop rule.

## Regression evidence

The new `stalled_agent_write_has_a_deadline_even_when_the_pipe_is_full` test
uses a private pipe whose server never consumes the oversized request. The
fixed transport returns `TimedOut` under the caller's deadline. The exact new
test source was also compiled against a legacy synchronous transport shim:
it failed, returning `BrokenPipe` only after the fixture's finite peer watchdog
closed the pipe (about 1.23 seconds). This verifies the old write-backpressure
failure without hanging the test runner; it was not a wholesale patch revert.

Other regressions cover silent and partial admin replies, uncertain-delivery
fallback, silent and truncated helper messages, full helper writes, a blocked
WSS connector, a late connector after stop, paused discarded-frame destruction,
and native-call stall observation.
These use private fixtures and simulated waits. They do not reproduce or prove
recovery from the NVIDIA driver hang, or qualify a live protected input route.

## Device serialization validation

Normal `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test` (**813 passed, 0 failed, 3 ignored**) and the release host build
pass from `host/`, including gate/coalescing tests and legacy-pattern negative
controls; the complete patch is not reverted for a test run.
The localhost probe reproduces a stalled `NvEncReconfigureEncoder` on
unmodified `67a7202` (**353 ms** first IDR, no rejoin IDR), while the candidate
completes both joins (**646 / 1,054 ms**) and connected phases
(**23.28 / 18.02 fps**, CPU **0.353 / 0.294%** of this 16-core machine).
Parked CPU is **0.0347%** with zero acquisitions, and both probe processes
exit during their own cleanup; reports live under
`host/artifacts/perf/device-lock-{before,after}-20261010/summary.json`.
The frozen baseline prevents a healthy performance comparison, and this short
ambient-desktop probe does not qualify long-term stability, client
decoding/presentation, protected desktops or the production relay.
