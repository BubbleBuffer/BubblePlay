# Host performance

The producer waits on capture, signalling-socket readiness and coalesced activity notifications. A desktop-duplication worker blocks in `AcquireNextFrame`, starts acquisition at the next frame admission time and transfers one owned frame lease to the producer. It releases that lease before acquiring again. Input, RTC/WSS events and cursor hooks wake the producer immediately. Agent reconnects attach the same notifier and wake for already queued events. Cursor event bursts coalesce at the existing 16 ms sampling cadence. Housekeeping waits are bounded to 100 ms; the stream-lab benchmark lease file (`%PROGRAMDATA%\BubblePlayenchmark-v1.json`) is read by a background thread once a second, so a slow disk cannot stall the session thread. The session adopts the latest result and treats one older than 5 s, missing or expired as no lease (production policy). The watchdog stages `housekeeping-lease` and `housekeeping-status` name those two calls in a stall report; cursor sampling uses a 100 ms heartbeat, with the previous 16 ms fallback when hooks are unavailable.

Desktop discovery runs on a 250 ms housekeeping timer and on capture errors. Security authorization stays fresh: native acquisition checks for the Default desktop immediately before acquiring, and the consumer checks again before exposing a desktop texture. GDI snapshots also check before and after copying. A cached RTC IDR records its source and checks Default again before replaying local Default pixels. Secure-desktop recovery retains its existing authorization boundaries.

Damage metadata is processed fully after frame admission. WSS accumulates a rectangle union, including both ends of moves, before admission so skipped frames retain their damage. Tile hashing reads damaged tiles and maps staging memory with `DO_NOT_WAIT`. A busy readback leaves hashes unknown and sends the change conservatively; it cannot suppress changed pixels as a no-op. Backpressure and settled-tile refinement schedule a bounded snapshot retry. GDI retries reuse the texture, surface and display DC. Caching a fresh IDR cancels startup snapshot retries; transport admission can retry that cached IDR. An overdue snapshot deadline wakes once, then waits for queue activity or housekeeping while admission is blocked.

On peer-left, the host releases input, parks acquisition and clears peer-specific media state while retaining capture, scaler, encoder, transport socket and signalling. Cursor hooks are removed; their message thread remains asleep and reinstalls hooks asynchronously when capture resumes. The next viewer requests a fresh IDR in place. WSS media sockets are replaced when their relay epoch changes; a changed encoder contract or real capture/signalling failure can still rebuild the affected resources. RTC resets use an ordered acknowledgment so events from the previous peer cannot complete the next peer's handshake. STUN refreshes run asynchronously on the retained transport socket.

A notification-only capture observer retains display-mode, console display-power and desktop-switch notifications while acquisition is parked. Healthy parked duplication has no recovery timer or frame acquisitions; a lost duplication retries recreation at a one-second cadence and awaits verified pixels. Viewer joins request an immediate authorized GDI snapshot when no DDA frame is ready, including after recreation, and Default checks before and after copying preserve the secure-desktop boundary. Parked capture defers recoverable Default-source status until pixels are verified; session-start and offer-state replay defer a recoverable Default-source `unavailable` status for at most two seconds; display-off recovery shares this short grace, while failed recreation and secure-desktop states remain visible, and input stays suspended until capture is verified. A silent driver loss without a Windows notification is discovered by the next viewer's acquisition and schedules an immediate recreation attempt.

The synchronous producer holds a thread-owned display and system execution requirement while a viewer is attached and clears it when the viewer leaves or the session exits. Unavailable local capture on Default triggers one zero-delta relative move through guarded local SendInput at most every two seconds; secure desktops retain their existing helper route. Capture-loss logs include the recorded cause and native DDA error code when available, and wake attempts and subsequent capture recovery are logged.

First-frame requests can arrive before ICE. They join one startup IDR, and retries of the same request report its existing admission. RTC admission is bound to the current generation and submitted access-unit ID; WSS admission is bound to the current media epoch. A request completed by presentation does not force a second IDR when repeated.

Decision (2026-10-15): add a late STUN mapping to the current RTC epoch and trickle it immediately, retaining it for later offers. Candidate mutations require a complete str0m output drain; reset acknowledgements retain the peer-event boundary. The regression failed before the fix and passes after it; a separate UDP fixture delivers a synthetic HEVC IDR through ICE/DTLS/SRTP without signaled remote host candidates. Neither test qualifies a hardware encoder, browser decoder or displayed picture.

The owner's 06:50 and 10:00 UTC failures never reached RTC readiness and submitted no access units. The host's "ICE connected" log actually follows str0m's DTLS connection event, so `no-idr-admitted` does not distinguish ICE from DTLS failure or prove an encoder defect. Only the 10:00 attempt lacked its public mapping when answering. The named UDP firewall rule also targets an old development executable rather than the installed path; packet drops were not verified. Browser playback and the separate fallback timeout remain unverified.

The browser viewer binds each trickled host candidate to the first remote m-line: `remoteIceInit` in `worker/public/receiver.js` sets `sdpMid` from the remote description, falling back to `sdpMLineIndex: 0`. Without either, [WebRTC's contract](https://www.w3.org/TR/webrtc/#dom-rtcpeerconnection-addicecandidate) rejects the candidate with `TypeError`. Covered by unit tests in `worker/test/receiver-ice.test.mjs`; not verified in a live browser.

Windows host builds select MSVC `link.exe` in `host/.cargo/config.toml` because the global rust-lld override can report success without executables. Root-level Cargo skips that configuration: hosted CI retains its default MSVC linker and job-level SDK path. Local root-level checks must set `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_LINKER=link.exe` explicitly.

Production NVENC resource registration remains per-frame. Persistent registration is still available to benchmark profiles; extending it to production needs separate lifetime and reconfiguration qualification. Tile readback does not use a staging ring or GPU hashing.

WSS v4 admission limits un-ACKed video by frame count and by airtime at the current bitrate, and skips the frame before encoding when either is exceeded. Both limits scale with the link's baseline RTT (the controller's 10 s minimum delta-frame ACK RTT): frames = clamp(ceil((rtt + 40 ms) / frame interval) + 2, 4, 12) and airtime = clamp(rtt + 120 ms, 150 ms, 400 ms). With no RTT sample the window is the old fixed 4 frames and 150 ms, so a relay or WAN link is no longer throttled by a cap sized for a LAN. The producer reports the stream's fps to the link for the frame interval. The pure rule is `inflight_window` in `host/src/wss_v4.rs`; the unit tests cover it, and the effect on a live relay link is unmeasured.

The link capacity estimate (`host/src/link_capacity.rs`) declares a link constrained only when ACKs show a queue that is deepening: at least three queue-evidence samples in two ACK bursts over 250 ms, and the RTT inflation over the minimum at the last sample exceeds the first's by 20 ms. A sender that outruns the link makes the queue deeper for as long as it does; a stalled or jittery path floods back a draining or flat backlog, whose slow deliveries are diluted by the stall and say nothing about capacity. Such a stall leaves the estimate and the rate untouched (on 2026-11-10/11 the old rule read 500 ms ACK stalls as 500-790 kbps links and cut 6 Mbps to the floor, with the link carrying 5-6 Mbps seconds earlier). Each `link constrained` log line carries the newest 16 delivery samples (see `docs/logging.md`) so a verdict can be checked against relay, browser or WAN stalls.

A sharp-viewport change on v4 starts a new media generation and forces an IDR of the cropped region; damage rectangles and tile refinement are mapped into the crop. The un-ACKed window and the capacity estimate are keyed by (generation, seq), so frames of the old generation retire when the first ACK of the new one arrives, and keyframe ACKs are left out of the delay controller's RTT samples, so a zoom change is not read as congestion.

Duplication, shared-device copies and NVENC operations take one retained lock per D3D11 device, and shared immediate contexts have verified multithread protection. `AcquireNextFrame` waits at most 16 ms under the lock; longer event waits stay outside it, and parked capture makes no acquisitions. Bitrate, QP, profile and reset requests coalesce into at most one reconfiguration immediately before a frame's registration and encode; a temporary refine rate restores on the next frame only when still needed.

An independent session watchdog reports a stage and `main.rs` line after ten seconds without progress, once per stall. Progress publication uses one atomic snapshot, including during parked housekeeping; it never acquires a logging or worker lock. NVENC call boundaries additionally report the exact native API and `encode.rs` line, including bitrate/profile reconfiguration and cleanup. This is diagnostic only: a driver call already stuck inside NVENC cannot be safely cancelled or its live device resources destroyed by the watchdog. See [the 2026-10-09 hang investigation](host-hang-2026-10-09.md).

`host/scripts/probe-host-performance.mjs` runs an isolated localhost WSS relay and records producer counters, process CPU and reconnect timing. It discards media payloads and uses no production credentials. It verifies host production and queue admission, not client decoding, image quality or protected desktop behavior. UAC, lock-screen, Admin mode, monitor changes and follow-active-window require live manual qualification, including `host/scripts/test-secure-desktop.ps1`.

## WSS relay capacity (Cloudflare Worker)

A stream that falls back to the WSS relay sends about 115 messages per second (about 50 are 20 ms Opus packets, the rest video, ctl and ACKs). Cloudflare bills incoming WebSocket messages (20:1) and CPU time; bandwidth is free. Measured in October 2026: roughly 0.2 ms of relay CPU per message.

Each PC has its own session Durable Object (`PcRelay`, named `pc-<device id>`), so streams of different PCs never share an object, its 32-connection cap or its CPU budget. One stream occupies one object with about 6 sockets, so the old limit of about 5 to 6 concurrent streams for the whole relay is now per PC. The front object (`relay-v1`) handles only gate, HTTP, admin and presence traffic; it sees no media. See [`relay-rs/README.md`](../../relay-rs/README.md) for the split.

Hot-path costs removed in the core (`relay-rs/core/src/relay/forward.rs`, `mod.rs`) and the adapter (`relay-rs/worker/src/pc.rs`): two `Conn` clones (four strings each) per binary frame, the action queue built for a batch of plain sends, and an alarm re-arm after every forwarded frame (activity only moves idle deadlines later, so a plain-send batch needs none).

Measured locally on Windows (2026-11-11), 188-byte frames, host to viewer:

| Measurement | Before | After |
| --- | --- | --- |
| Core `on_binary` per frame, native release (`cargo test --release -p bp-relay-core --test forward_bench -- --ignored --nocapture`) | 359 ns | 189 ns |
| workerd CPU per forwarded frame, whole pipeline (`node relay-rs/worker/scripts/bench-forward.mjs`) | 0.618 ms (single object, before the split) | 0.50 to 0.53 ms |

The end-to-end number is dominated by workerd's WebSocket and JS boundary work, which the relay code does not control, and it varies by about 5 percent between runs. Local workerd is not Cloudflare's CPU accounting: use the ratio, not the absolute value. Message count is what the bill follows, so the larger saving is fewer messages (see the 20 ms audio frame note below).

The host sends 20 ms Opus frames (960 samples per channel) on the WSS path, so audio is 50 packets per second there; WebRTC keeps 10 ms. The BPA1 header carries samples per channel, and the browser (`audio.js`), Android and Windows viewers accept 480 and 960 and reject anything else. The shared fixture `fixtures/audio-contract.json` pins both. The silence gate still works in 10 ms steps, so silence is sent for about 200 ms as before.
