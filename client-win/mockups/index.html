BubblePlay for Windows: UI mockups

OverviewConnect flowSession chrome

Static review mockups for the native viewer (egui on D3D11, 2026-10-13). Nothing is built yet. Each page has a state switcher (buttons or number keys) and design notes at the bottom.

Connect flow

Device-key model: Your PCs, pairing (enter code, compare number), vouch request, site gate, before-sign-in approval, connecting, connect failed, key refused, ID rotation, and This PC (hosting this computer: status, tray settings, paired devices, pairing requests).

Session chrome

Collapsed tab, toolbar, monitor picker, stats, capture and release toasts, reconnecting, Admin required, secure desktop.

Direction

The stream owns the window. Chrome is near-opaque warm duvet, attached to the top edge like a cut tab, and only bright apricot says "live" or "captured". Out of session, the app is calm and left-aligned with one confident Bricolage moment per screen and a single apricot action.

What should make it feel better than the browser: native speed (no page loads), keycaps that teach the escape chords, states that always say what survived, and one click from Your PCs to the session with that PC's last mode.

Shared tokens

Same family tokens as worker/public/bubbleplay.css; fonts are copies of worker/public/fonts. Fitted radii: control 7 11 6 9, field 6 10 6 8, panel 12 18 10 16, edge strip 0 0 10 12. Spacing on a 4 px base.

Icons

Lucide, verbatim from lucide-static@0.460.0 (ISC), bundled as a sprite in icons.js. In egui: rasterise the same SVGs to textures at 16/18/22 px for 1x, 1.5x and 2x DPI.

Out of v1

File transfer and clipboard are not drawn. Their slot is reserved in the strip between Stats and Settings.

Settled from the docs

  1. Relay vs PC. Today one relay is one room, so one PC. With device keys, rooms are keyed by PC ID and one relay can front several PCs; one viewer holds several PCs, each with its relay URL (device-keys.md). The list shows PC ID and online state from the relay.
  2. Approval code and timeout. Site-gate and browser approval have no code to match: ntfy carries Approve/Deny links. Go relay approvals expire after approvalTTLSeconds (30-120 s, default 90); approval lasts 30 days. Pairing does use codes: a 10-character one-time code (5 minutes) and a 6-digit comparison number on both sides; remote pairing requests expire after 10 minutes.
  3. Home and mode. Home A is the one. No choices before connecting: the session opens in the PC's last mode, or Game for a new PC; mode changes live in the strip.

Open questions for the owner

  1. Site gate for the native viewer. The gate covers browser-facing paths and Android is exempt. Is the Windows viewer exempt too? The mockup shows the gate screen in case it is not.
  2. Windows viewer key storage. The storage table covers browser, Android and the host PC, not a native viewer. Mockup assumes DPAPI, no passphrase, like the host.
  3. Default mode for a never-used PC. Mockup assumes Game.
  4. Before sign-in second factor. device-keys.md allows ntfy or an authenticator code checked by the logon host; unattended-access.md says ntfy sent by the PC, and TOTP goes away at cutover. Mockup shows ntfy only.
  5. Copy and timings the docs leave open: wrong code or mismatched number on pairing, denied vouch, voucher validity (proposed 10 minutes), Cloudflare approval TTL, re-pairing after a revoke, recovery after "PC key changed", and the rotation UI (where Replace key lives).
  6. Revoked vs unknown. The native socket closes without a reason, so the viewer shows one message for both. Should the relay send a reason?
  7. Strip height (42 px here, 32 px in the browser) and the proposed stats chord Ctrl+Alt+Shift+S.

What v1 can wire up today

  1. Works with today's relays: connecting, connect failed, the session chrome, and approval wait as browser approval (ntfy or the host dialog "Allow a new browser to sign in?"). Today the client still signs in with the relay password (Go: password plus TOTP; Cloudflare: password), so v1-today needs a plain password step that these mockups no longer draw.
  2. Waits for device keys in the host and relay: pairing, vouching, PC IDs and online state in Your PCs, several PCs per relay, key refused, PC key changed, ID rotation, before-sign-in approval (also waits for unattended access).
  3. Site gate: approval exists today as browser approval; the 30-day __Host-gate cookie in front of every path arrives with the device-key cutover.

This PC: the tray today, mapped to the app

  1. Status line (Starting, Running, Restarting in N s, Stopped, Stopped (not configured)) → the status pill in the This PC row and panel.
  2. Viewer connected (host stdout markers and the Admin agent demand event) → "Pixel 8 connected since 09:12" and the Connected tag on that device.
  3. Restart host → Restart. Quit (also --quit) ends the tray and the host → Stop hosting / Start hosting. The tray has no stop that keeps the tray running.
  4. Stream PC sound (tray.json, restarts the host), Admin mode (UAC helper on, scheduled task off), Start at login (tray.json plus HKCU Run) → the three switches.
  5. Host build line, Roll back host, Open logs folder → the footer row.
  6. Admin agent / secure helper "needs update" lines and the secure desktop status → an inline notice in the panel when they apply (not drawn).
  7. Balloons (Admin mode, update failed or rolled back) → the same messages as notices in the panel; the tray keeps its balloons.
  8. "Allow a new browser to sign in?" is a host window, not the tray; the pairing request card uses the same decision.

Missing today

  1. No control interface. The tray takes only --quit and the --send-files spool: no pipe, no localhost HTTP. Everything the panel reads or changes needs the local control interface: status, viewer connected, start, stop, restart, roll back, the three switches, build and update state, browser approval decisions. Admin mode off alone could run the existing scheduled task; on needs the elevated helper (one UAC prompt from the app).
  2. CPU mode is not in the tray or the host yet (encoders lane).
  3. Paired devices, revoke, May vouch, pairing requests and the PC ID wait for device keys.
  4. Open logs folder needs no endpoint (the app opens %LOCALAPPDATA%\BubblePlay\logs itself).

Open questions (This PC)

  1. Who owns settings? The tray keeps tray.json in memory and overwrites it on save, so a direct edit from the app is lost. Should all writes go through the tray (or host) over the control interface?
  2. Where does the control interface live: in the tray (which supervises the host) or in the host?
  3. Stop hosting: stop the host but keep the tray running (new), or quit both like today?
  4. CPU mode options and whether changing it restarts the host like Stream PC sound.
  5. Approvals in two places: when the app is open, does a pairing request or browser approval still show the tray notification or host window too, and does deciding in one close the other?
